# 04.5 — Mechanical test gate outside the lock

Design of record. Written to CX's TURN-231 pins, revised to TURN-232 (3 Blocking + 2 Important + the
phase-graph ruling) and to TURN-233 (1 Blocking + 3 Important), TURN-234 (1 Blocking + 4 Important) and TURN-235
(2 Blocking + 4 Important + 1 optional). **No code exists yet.**

TURN 232 corrected the TURN-231 lifecycle order; this document follows the corrected one.

## Authority and non-goals

The gate is the sole authority deciding a mechanical test outcome. It owns the attempt lifecycle, the
durable attempt record, and the identity proof of what was tested. It does not own phase edges (the
engine does), run identity (attach), or the review packet (04.3).

The runner returns **facts**, never a verdict. Mapping facts to an outcome is the gate's; the engine
consumes the outcome. A runner bug must not be able to become a verdict.

**Non-goal:** the cancel *lifecycle* (05.7). 04.5 ships the durable per-attempt cancel-REQUEST
primitive and the state shape 05.7 needs — the coherence problem is solved here, not deferred.

## Slice order

1. **`internal/proctree`** — authority-neutral leaf.
2. **The schema step, ATOMIC** — run-policy v2 (D016 amendment) + attempt record/store contract +
   RunState **v8**, one commit. Policy v2 cannot land alone: state embeds the frozen policy and its
   decode calls the current policy validator.
3. **The lifecycle machine** — start / run / finalize / recovery + crash matrix.
4. **Composition** — coordinator/engine/submit/status wiring, the `FixReturn == VERIFY` route change,
   the VERIFY packet entry, and the adversarial route tests.

## 1. `internal/proctree` — containment (TURN-233 pin 1)

`PR_SET_PDEATHSIG` is unusable as the owner-death trigger on two counts: it applies to the **direct
child only** and is cleared in that child's forked children, so it is not transitive; and it is scoped
to the **creating THREAD**, not the process (TURN-236 pin 1, below). A bare PGID persisted for a later
process risks PID reuse. Containment is named per platform with the executable that provides it and
the guarantee it actually gives.

| Platform | Mechanism | Executable | Guarantee |
|---|---|---|---|
| Windows | create the **UNNAMED kill-on-close Job Object** with breakaway denied FIRST, then create the process **suspended with that job in `PROC_THREAD_ATTRIBUTE_JOB_LIST`** so assignment is atomic with creation, **observe the whole containment claim** (membership, kill-on-close in force, both breakaway flags absent), then resume | none extra | **transitive and non-escapable by the command's own authority.** The coordinator holds the only handle — structurally, because there is no name to reopen — and its death closes the handle, at which point the kernel kills the job. |

**The Windows job is UNNAMED, corrected at TURN-265 after a native probe (CX pin 1, confirmed
independently on CC's host).** The row above previously said *named and attempt-bound*, and that could
not support the guarantee beside it. A named job is reopenable with `OpenJobObject` by anyone holding
the creator's authority — and the test command runs with exactly that authority — so a command that
learned the attempt-bound name could hold its own handle and prevent kill-on-close from ever firing
when the coordinator died. Measured non-elevated, Windows 11, Go 1.26.5:

| Probe | Result |
|---|---|
| plain named job, reopen by name | **succeeds** |
| after the creator closes its handle | name **still resolves**; the second handle keeps it alive |
| after the last handle closes | name gone (`ERROR_FILE_NOT_FOUND`) |
| empty DACL (`"D:"`), reopen all-access / query | **denied** |
| empty DACL, reopen with `WRITE_DAC` | **succeeds** — the object manager always grants the OWNER `READ_CONTROL` and `WRITE_DAC` regardless of the DACL |
| after rewriting that DACL, reopen all-access | **succeeds** |
| `Global\` job created and reopened non-elevated | **succeeds** |
| unnamed job | created; no name exists for `OpenJobObject` to be given |

So an ACL is a speed bump rather than a barrier: the same-user owner can always rewrite it. The
resolution is to remove the attack surface instead of guarding it. **`Global\` is dropped as well** —
CX's pin 2 is correct that `SeCreateGlobalPrivilege` does not gate job objects and the premise behind
the earlier session-id BLOCK was false, but with no name at all the whole session-namespace question
stops existing.

**What the unnamed job costs, and what replaces it.** The completion fact can no longer be a name
lookup. It does not need to be. Kill-on-close is enforced by the KERNEL when the last handle closes,
and process exit closes every handle a process held, so on Windows **owner death IS the teardown**,
with no intermediary that could fail — which is exactly what the Linux receipt exists to prove because
there the killing is done by a process that might not manage it. Windows recovery therefore reads owner
death (an unheld lease), and the honest narrowing is that it knows every member was **terminated**, not
that every member was **reaped**: with no handle left there is nothing to enumerate the domain with. A
live coordinator still observes the drain directly through the handle it holds.

**The residual limit, stated as such.** This is not a defence against a same-user adversary attacking
the COORDINATOR — duplicating the job handle out of it, injecting code, or terminating it. Nothing
unprivileged can defend that, and it is the same class as the Linux `setsid` escape already placed
outside the authority model. The difference that matters is that the NAMED design let the contained
command escape using nothing but its own authority, with no attack on the coordinator at all.
| Linux | direct child is claudex re-executed via `/proc/self/exe` in a **guarded supervisor mode**, which detects owner death by **EOF on an inherited pipe**, becomes a **child subreaper**, puts the real command in its own **process group**, and kills + reaps that group | the **same claudex binary** — no second artifact, so the single-distributable-binary property holds | **ordinary descendants only.** A task-controlled child holds the user's OS authority and may `setsid` out of the group; that descendant is NOT contained. |
| other POSIX | fresh process group, best-effort kill by the live owner | none | **none after owner death.** |

`os/exec` cannot install a Go signal handler between fork and exec, which is why the supervisor must
be a real re-executed process rather than a callback.

**Owner death is detected by pipe EOF, NOT by `PDEATHSIG` (TURN-236 pin 1).** `PR_SET_PDEATHSIG` is
tied to the **creating THREAD**: the signal fires when the thread that forked the child terminates,
even while the process keeps running. The Go runtime migrates goroutines across threads and retires
idle ones, so an `os/exec` fork from an ordinary runtime thread could fire cleanup **spuriously** —
killing a healthy test run and reporting a false mechanical outcome. That is a correctness bug, not a
missing hardening.

The **process-lifetime authority is the inherited `ctrl` pipe** (the full two-pipe protocol is pinned
below): the coordinator holds its sole write end for the supervisor's entire lifetime, and the
supervisor watches the read end for **EOF** through command execution and cleanup. Process exit closes
every descriptor the process held, so EOF is a process-lifetime signal by construction, with no thread
affinity. That same pipe carries the handshake and control frames, so death detection is not a
separate mechanism bolted alongside the protocol.

Two descriptor obligations make "sole write end" true rather than assumed:

- the **task** never inherits either end — they are `FD_CLOEXEC` (never *closed*: the supervisor
  needs them) before the real command is spawned, since a task holding the write end would postpone
  EOF indefinitely;
- **no other coordinator child** inherits the write end either. It is `CLOEXEC` in the coordinator and
  passed only via the explicit inherit list for this one supervisor, because any other holder would
  keep the channel open past the coordinator's death.

`PDEATHSIG` is **not adopted at all**, not even as defence-in-depth. Its only failure mode here is a
spurious kill of a healthy run, and the channel already covers what it would have covered, so keeping
it would add a flake class in exchange for nothing. Revisiting it would require a pinned
`runtime.LockOSThread` owner kept alive until the supervisor is reaped, plus the thread-semantics and
false-positive tests — a decision row, not a default.

**Launch ordering: the containment is armed DORMANT before the active CAS (TURN-236 pin 2).** The
crash row "after active CAS, before spawn" required the §1 completion fact, and §1 BLOCKS when the
fact is absent — but if the coordinator died before the supervisor existed, no process could ever
publish a receipt, so that row's "ledger-only interrupted; explicit retry" was **unreachable** and the
real behaviour would have been a permanent block. Ordering fixes it at the source:

1. durably publish the intent;
2. **arm the containment with no command in it** — on Linux spawn the supervisor, complete the
   handshake, and let it take the lease and the receipt authority while it blocks awaiting **GO**; on
   Windows create the **unnamed** job and hold its sole handle;
3. **CAS** the active attempt;
4. release the run guard;
5. send **GO**, and only then does a command spawn.

Because arming precedes the CAS, any state that carries an active ref is a state in which the receipt
authority already existed. Owner death before GO is seen as EOF by a supervisor that has started
nothing, and it publishes a **no-command cleanup receipt** — a completion fact that is truthful and
cheap, since there is nothing to kill. Every launch cut is now covered, not only the handshake cuts.

On Windows the same ordering makes the containment exist before any process does, and
`PROC_THREAD_ATTRIBUTE_JOB_LIST` removes the create-suspended-then-assign window in which a process
existed outside the job. **Windows has no post-crash completion fact at all** (below), so the value of
arming first is not that it publishes something — it is that a coordinator which dies before the CAS
had nothing running to leave behind, and the empty job dies with it.

**Scope of the guarantee (TURN-233 pin 1, corrected at TURN-233 → 234).** Only Windows gives a
transitive, non-escapable proof. The previous draft said escape is *unobservable* and then required
recovery to BLOCK when escape occurred — a branch **no available fact can select**, since the escaped
descendant stays alive while the supervisor truthfully proves only that its old PGID is empty. A test
asserting that branch could only have simulated a receipt, proving nothing about the real case. It is
removed rather than faked.

The honest Linux contract:

- **In the authority model:** descendants that remain in the owned **containment domain** (the process
  group on Linux, the job object on Windows). The supervisor kills and reaps them, and a clean reap
  permits retry — but only when a **durable fact proves the reap completed** (below).
- **Outside the authority model:** a descendant that deliberately `setsid`s out. The test command runs
  with the user's OS authority, so this is not preventable by an unprivileged supervisor and not
  detectable afterwards. It is a stated limit, not a guarantee with a hole in it.
- **Residual risk and its real mitigation:** an escaped process could still mutate the worktree. The
  gate does not claim to have contained it, and — correcting an earlier overstatement — identity is
  **not "total" either**. An escaped process can mutate immediately after any observation. What
  identity gives is **repeated linearization points** (attempt start, result finalization, and the
  verifier-submit recheck), each of which fails the attempt if the tree differs at that instant. That
  is strictly weaker than continuous detection and is stated as such.
- A kernel-backed containment (delegated cgroup v2, PID namespace) would make escape observable or
  denied, but neither is portably available unprivileged. Adopting one is a **future decision row**,
  not a claim made here.

**The durable completion fact (TURN-235 pin 1).** "Clean reap permits retry" needs a fact recovery can
actually read. After coordinator death recovery cannot `wait` a reparented supervisor, an unheld lease
proves only that its owner died, and a persisted PGID is already rejected for PID reuse. So each
platform publishes an observable completion fact, and its absence blocks:

- **Linux:** the supervisor **holds the lease through cleanup** and, before releasing it, durably
  publishes a rooted, attempt-bound **`cleanup.receipt.v1.json`** (attempt id, whether a command was
  ever started, the **command** PGID when one was — absent on a no-command receipt, since the group
  cannot exist before the command — reaped count, the group-empty proof, completion timestamp) into the
  attempt root. It can do this because the inherited bounded authority (§1, handshake) includes a
  directory handle for exactly that attempt — not a caller-chosen path. Recovery verifies the receipt
  is present, attempt-bound, and durable; **no receipt, or ambiguous durability, BLOCKS**.
  **A truthful reap count requires being a subreaper (TURN-236 pin 3).** The supervisor is the parent
  only of the command leader; ordinary grandchildren are not waitable by it once they orphan, so
  "reaps the group" and a `reaped count` were claims the stated mechanism could not support. The
  supervisor therefore sets **`PR_SET_CHILD_SUBREAPER` before spawning the command**, so orphaned
  descendants reparent to it and become waitable. The sequence is exact, and the receipt is published
  only at its end:
  1. signal the whole process group (`kill(-pgid, ...)`), not just the leader;
  2. reap with **`waitpid(-pgid, ...)`**, scoped to the owned group — never a bare wait-for-any-child
     (TURN-237 pin 4, rationale **corrected** at TURN-255). The original reason recorded here was that
     an unqualified wait would **block** on an out-of-model child forever. That is **false** for this
     design: the drain is `WNOHANG` and cannot block, and a sound mutation harness disproved it by
     swapping `-pgid` for `-1` with no test noticing.
     The real reason is ownership of the COUNT. A `setsid` escapee is outside the containment model,
     but because the supervisor is a subreaper that escapee still **reparents to it** — so a bare
     wait-for-any-child would reap processes that are not ours, consuming their exit status and
     inflating the `reaped` total that the cleanup receipt and the `TERMINAL` both bind. Group scoping
     keeps that number a statement about the owned group;
  3. **iterate**, because `ECHILD` and group-empty are different facts. `ECHILD` says only that
     nothing in the group is currently a child of the supervisor, which can be true **before** an
     in-group grandchild has reparented. So alternate `waitpid(-pgid, WNOHANG)` with a
     `kill(-pgid, 0)` probe until the probe returns **`ESRCH`**. A single post-`ECHILD` probe had no
     defined next step for the case where it found the group non-empty;
  4. bound the loop with a **cleanup deadline**. On expiry the supervisor publishes **no success
     receipt** and exits, so recovery finds the proof absent and **BLOCKS** — the honest outcome,
     since a group that will not drain is exactly the case nobody should retry over;
  5. only on `ESRCH` publish the receipt.
  Two required tests: **the leader exits promptly while a background grandchild survives it** — the
  shape a direct-child wait silently passes — and a **live `setsid` escape**, proving cleanup neither
  waits on the out-of-model child nor falsely receipts the group as drained.
- **Windows: there is NO post-crash completion fact, so recovery BLOCKS — same as other POSIX
  (corrected at TURN-266, CX pin 2).** Kill-on-close being *requested* is not observable, so it is
  **read back** — at arming and again while the command is still suspended, since the claim is about
  the limits in force at the moment the command runs. That secures the LIVE path. It does not produce a
  fact a later process can read.
  The previous draft said the completion fact was **owner death itself**, on the reasoning that the
  kernel terminates every member when the last job handle closes and process exit closes handles
  unconditionally. Each half is true and the bridge between them is not: **the lease and the job are
  different handles**. `internal/oslock` is a file lock, released when ITS handle is closed; observing
  the lease unheld establishes only that the lease handle was processed. Windows documents that process
  termination closes all kernel objects but specifies **no order between handles**, so a recovering
  coordinator can observe UNHELD while job termination is still in flight — and would then retry over a
  domain that is dying but not dead. That is an ordering assumption, not a guarantee, and it is
  withdrawn rather than tested: a test written against it could only have measured how fast this
  machine happens to be.
  So on Windows: a crash leaves **no readable proof**, and recovery **blocks for operator action**.
  Note what is NOT lost — containment still holds. The tree really is terminated; what is missing is
  something a later process can READ to know it. The clean-shutdown path is unaffected, because a live
  coordinator terminates the job, observes the domain empty through the handle it holds, and only then
  releases the lease — that ordering is the coordinator's own and is provable.
  **Decision row, not a claim: a Windows supervisor would restore automatic retry.** The Linux
  architecture ported — a re-executed child that holds the job handle, watches the coordinator for EOF,
  tears down, publishes `cleanup.receipt.v1.json`, then exits — would give Windows the same surviving
  cleanup authority and the same readable fact. It contradicts the current "Windows has no supervisor
  and therefore no IPC" and is a real addition, so it is recorded here for ruling rather than assumed.
- **Other POSIX:** no completion fact exists, so recovery **blocks** for operator action, as before.

**The supervisor IPC is a two-pipe protocol, not a one-way pipe (TURN-237 pin 1).** The previous
draft had a single parent-to-supervisor pipe carrying liveness, which cannot carry the protocol the
gate actually needs: the supervisor must signal readiness, the coordinator must send timeout and
cancel **during** execution, and the coordinator must receive the exact spawn/exit/signal facts that
become `result.v1.json`. Deriving those facts from the supervisor's own exit status would conflate a
genuine command **exit 127** with a supervisor that itself failed — the record would attribute an
infrastructure fault to the code under test, which §9 exists to prevent.

Two unidirectional pipes, each with one unambiguous EOF meaning. A `SOCK_SEQPACKET` socketpair would
also work; two pipes are chosen because the EOF authority is then per-direction and explicit rather
than derived from shutdown state.

| Pipe | Coordinator holds | Supervisor holds | Direction | EOF means |
|---|---|---|---|---|
| `ctrl` | write end (**sole** holder) | read end | coordinator → supervisor | **the owner died** — the death authority above |
| `stat` | read end | write end (**sole** holder) | supervisor → coordinator | **the supervisor is gone** |

- **Frames are versioned, bounded and length-prefixed**: fixed magic, `u16` version, `u16` type, `u32`
  payload length, then the payload. `ctrl` carries `GO{challenge}` and `CANCEL`; `stat` carries
  `READY{challenge}`
  and `TERMINAL`.
- **Every frame is one blocking write of at most `PIPE_BUF` (TURN-238 pin 4).** The ceiling is a
  contract, not a convenience: POSIX makes a pipe write of at most `PIPE_BUF` bytes atomic, so a
  frame is delivered whole or not at all. The supervisor path is Linux-only, where `PIPE_BUF` is
  **4096**, and that is the hard ceiling for every frame including `TERMINAL` — which is why
  `TERMINAL` carries only bounded scalars (`command_started`, exit code or signal, spawn-failure
  class, command PGID, reap counts) and never stream data.
  **Success is the complete frame write, nothing less.** On a short write or any write error the
  coordinator closes `ctrl`, and the supervisor treats **EOF with an incomplete frame in hand as
  ABORT** — it starts nothing and cleans up. Without this pin the earlier claim was unsound: a
  coordinator could observe a write error while the supervisor had already assembled a complete `GO`
  and started a command, which would make `command_started: false` a false record. The adversarial
  short-write seam is a required test, not an inference.
- **`TERMINAL` is the only authoritative source of runner facts** — `command_started`, then either
  `exit_code` or the terminating signal, or the spawn-failure class when the command never started.
  An exit 127 therefore arrives inside a **well-formed frame**, while a dead supervisor is **EOF on
  `stat` with no `TERMINAL`**. The two are structurally distinguishable, which is the entire point.
- **Malformed, truncated, over-length and unknown-type frames are refused, not tolerated.** A bad
  `ctrl` frame is fatal to the supervisor: kill the command if one exists, run cleanup, exit. A bad
  `stat` frame makes runner facts untrustworthy, so the coordinator marks the attempt
  recovery-required instead of reading a partial frame as an outcome. A truncated `GO` is **not** a
  `GO` — guaranteed by the one-write/`PIPE_BUF` rule above, not merely asserted.
- **stdout/stderr stay separate and are never relayed.** The coordinator creates both stream pipes and
  passes only their **write** ends through the supervisor to the command, so the coordinator reads,
  redacts and digests without the supervisor ever touching stream bytes.

**Descriptor ownership, stated per phase (TURN-238 pin 1).** The previous draft said the supervisor
"closes / `CLOEXEC`s every capability FD before the real command starts", which **contradicted the
protocol it was introducing**: closing `ctrl` destroys owner-death detection and `CANCEL`, closing
`stat` destroys terminal reporting, and closing the stream write ends before `Start` means the command
never receives them. The rule is `CLOEXEC`, **not close** — and for the stream ends, close only
*after* a successful `Start`.

| Descriptor | Coordinator | Supervisor at `READY` | Supervisor pre-`Start` | Command child | Supervisor post-`Start` |
|---|---|---|---|---|---|
| `ctrl` write | **holds, sole**, for the supervisor's whole lifetime | — | — | never | — |
| `ctrl` read | — | holds (arrives inheritable) | sets `FD_CLOEXEC` | never | **retains** — EOF and `CANCEL` both need it |
| `stat` read | **holds**, drains to EOF | — | — | never | — |
| `stat` write | — | holds (arrives inheritable) | sets `FD_CLOEXEC` | never | **retains** until `TERMINAL` is sent |
| `stdout`/`stderr` write | closes its copies immediately after handing them to the supervisor | holds both | assigns them as the child's stdout/stderr | **receives as fd 1 / fd 2** (the `dup2` clears `CLOEXEC` on the child's copies) | **closes its copies immediately after a successful `Start`, and on every failure path** |
| `stdout`/`stderr` read | **holds**, drains both **concurrently** | — | — | never | — |
| **stdin (fd 0)** | — | — | opens the **null device** `O_RDONLY` | **receives as fd 0** | closes its copy immediately after a successful `Start` |
| `spec` read | — | reads the execution spec to EOF, validates, **closes before `READY`** | already closed | never | — |
| `spec` write | writes the bounded spec, then closes | — | — | never | — |
| **attempt directory FD** | opens `O_DIRECTORY` and passes it | holds (arrives inheritable) | sets `FD_CLOEXEC` | **never** | **retains through durable receipt publication**, closes in terminal step 5 |
| **lease FD** | — | opened by the supervisor via `openat` on the directory FD, then locked through the **one attempt-lease API** (below) | sets `FD_CLOEXEC` | **never** | **retains through cleanup**, released in terminal step 5 |

- **`FD_CLOEXEC` is what keeps the task out**, and it is set explicitly because the inherited FDs
  arrive *inheritable* — they had to be, to be passed at all.
- **stdin is the null device, never an inherited terminal (TURN-241 pin 3).** The table previously
  defined fds 1 and 2 and said nothing about fd 0, which left the mechanical gate free to inherit the
  coordinator's or supervisor's stdin: a test command could then **block waiting for input** — hanging
  until the timeout and reporting a `fail` that says nothing about the code — or **consume operator
  data** from a shared terminal. It also left the exact-set `/proc/<pid>/fd` assertion undefined,
  since fd 0 would be present but unspecified. The child gets the null device, and the test proves a
  read returns **EOF promptly** rather than blocking.
- **The capability FDs are in this table because their non-inheritance is what protects the completion
  fact (TURN-239 pin 1).** The earlier table covered only control and stream FDs, which left the two
  that actually matter unstated. If the **lease FD** reaches the command, an OFD lock lives as long as
  any descriptor referencing that open file description, so the task would hold the lease **past
  supervisor death** and recovery would read a live owner that does not exist. If the **attempt
  directory FD** reaches the command, the task holds a writable handle to exactly the directory
  `cleanup.receipt.v1.json` is published into, and can interfere with the completion fact it is
  supposed to be judged by. Both are `FD_CLOEXEC` before `Start`.
- **The lease is acquired by the supervisor, not handed to it** — `openat` on the inherited directory
  FD, so the path cannot be caller-chosen, and there is no coordinator-to-supervisor handoff window in
  which the lease is held by nobody.
- **One lease primitive, used by BOTH acquire and probe (TURN-240 pin 1).** An earlier draft specified
  `F_OFD_SETLK` here while the repository's existing lock is `flock`
  (`internal/oslock/oslock_unix.go:14-30`). **Those families do not contend with each other**, so a
  probe written against one would report a lease held by the other as *unheld* — and "held vs unheld"
  is what the whole concurrency and recovery story turns on (§5), so the failure would not be a
  cosmetic mismatch but a live owner reported as dead.
  The attempt lease therefore **reuses `internal/oslock`** rather than introducing a second family:
  the same `flock` primitive, extended with a rooted `openat`-based acquire and an explicit
  **nonblocking probe**. Its semantics are exactly what this design needs and already tested —
  associated with the open file description, released by the kernel on process exit, and contended by
  a *distinct* `open` of the same file.
  **The probe contract:** take the lock **nonblocking on a distinct open file description**; treat
  contention as **held**; on success release **immediately**, having proven only that nobody held it
  at that instant; and **fail closed** on any error or unsupported platform rather than reporting
  unheld. A probe that reports "unheld" because it errored is the same defect in a different costume.
  **Test that the families cannot be silently swapped:** hold the lease with the chosen primitive and
  assert that a probe using the *other* family observes it as unheld. That test exists to fail loudly
  if anyone substitutes one for the other, which is the mistake this pin is correcting.
- The stream write ends are the only descriptors the command receives. If any copy survives anywhere
  else, the coordinator never sees stream EOF, so each close above is load-bearing rather than tidy.
- **Every pipe gets an EOF test**: `ctrl` read EOF iff the coordinator process is gone (or aborted
  deliberately); `stat` read EOF iff the supervisor is gone; `stdout`/`stderr` read EOF iff the
  command has exited *and* no stray copy is held — which is the assertion that proves the closes.
- **Non-inheritance is tested directly, not inferred from EOF.** Four pipe EOFs say nothing about the
  directory and lease FDs, which have no EOF to observe. The test enumerates the child's
  `/proc/<pid>/fd` and asserts it contains exactly the expected descriptors, and separately proves an
  inherited-FD use FAILS — a command that tries to write through a leaked directory FD or hold the
  lease must not succeed.
- **What authorizes the supervisor, stated without overclaiming (TURN-239 pin 3).** The earlier text
  said the nonce "proves the sender is the process that spawned this supervisor". It did not: the
  supervisor had no independently known expected value, so accepting an arbitrary first nonce proved
  only possession of the `ctrl` write end — which is *already* the authority, making the nonce
  ceremony rather than proof.
  **The capability is exclusive endpoint inheritance**, full stop: only the coordinator holds the
  `ctrl` write end, and an unrelated caller of the internal route inherits nothing and can do nothing.
  On top of that, `READY` now carries a **supervisor-generated challenge** that `GO` must echo. That
  is worth having for what it actually gives — proof that the `GO` came from a party that read *this
  instance's* `READY`, so a coordinator bug that reused or misrouted a write end across attempts is
  caught rather than obeyed. It is not claimed to add authority against a party who already holds the
  write end, because it does not.
- **The frame protocol is a state machine, not just a set of typed frames (TURN-239 pin 3).** Type
  validity without state validity would let a well-formed **duplicate `GO`** be read as a second
  launch. Pinned: exactly one `READY`; exactly one valid `GO`, and a second `GO` is **fatal**;
  `CANCEL` **before** `GO` is a no-command abort (nothing starts, cleanup runs, the no-command receipt
  is published); `CANCEL` **after** `GO` is idempotent, so repeats change nothing; exactly one
  `TERMINAL`, and a duplicate makes the attempt recovery-required on the coordinator side; every
  out-of-state frame is fatal on the side that receives it.
- **Windows has no supervisor and therefore no IPC**: the coordinator holds the process and job
  handles directly and reads exit facts from the process handle, so there is no intermediary whose
  failure could be mistaken for a command exit.

**How the command crosses the re-exec boundary (TURN-239 pin 2).** The design told the supervisor to
spawn a command without ever saying where it gets one. `GO` carried a nonce; the attempt intent binds
only the environment *identity*; the resolved values live in RunState on the coordinator's side of a
process boundary. Nothing said how the resolved executable, argv (including intentional **empty**
elements), the exact frozen environment and the cwd reach the supervisor — so the natural
implementation would have been the supervisor reading state or its own ambient environment, which is
precisely what `ResolvedExecution` exists to prevent.

**A bounded, immutable execution spec on its own inherited FD**, with its digest bound in the attempt
intent:

- `exec.spec.v1` is canonical and carries the **resolved absolute executable path**, the argv array
  losslessly (empty elements preserved — a canonical array, never a shell-ish string), the cwd, and
  the exact frozen environment as an ordered name/value list.
- **Canonical JSON is not byte-lossless, so environment and argv are carried as base64 (TURN-240 pin
  2).** "Byte-for-byte child environment equality" and a JSON string field are incompatible on Unix,
  where an inherited value may contain **invalid UTF-8**: canonicalization replaces or normalizes
  those bytes, so the digest would bind something the child never receives. This is the same defect
  found at TURN 216 for git paths and fixed there with `path_b64`; I did not carry the lesson across.
  Environment **names**, environment **values** and **argv elements** are therefore base64-encoded on
  the wire, in **every** carrier of the execution view. One grammar **within the execution view** —
  the aliasing bug at TURN 216 came from two encodings meeting for the same field on the same wire,
  and that is what this prevents.
- **The source-policy boundary is real and intentional, so it is stated rather than claimed away
  (TURN-241 pin 4).** "One grammar in all carriers" was too broad: `EffectivePolicy` persists the
  operator's argv in **plain UTF-8** and must keep doing so, because the durable invariant
  `reflect.DeepEqual(ParseRunPolicy(PolicyCanonical), EffectivePolicy)` requires it. There are
  therefore two views, by design:
  - the **source policy** — operator-authored, plain UTF-8, byte-equal to what was parsed;
  - the **execution view** — base64 throughout, in one grammar.
- **The execution view has TWO derivations with different timings and different carriers (TURN-242
  pin 1).** An earlier draft said the derivation happens "exactly once, at attach" and listed
  `ResolvedCommand` among the bootstrap/state-bound fields. That is impossible for a value §2
  deliberately resolves at **attempt start**, and it is the rejected shape restated — the same
  stale-clause contradiction, this time inside text written to fix a different one. Split:
  - **Environment execution view** — `ResolvedExecution`. Derived and validated **once, at attach**,
    from the immutable `EffectivePolicy` and the ambient environment, and **bound durably** in the
    `BootstrapIntent` and RunState v8. Nothing re-derives it.
  - **Command execution view** — `ResolvedCommand`. Derived **at each attempt, under the run guard**,
    from the immutable `EffectivePolicy`, the frozen environment and the **current accepted
    worktree** — because the executable may not exist before that commit. Carried **only** in the
    attempt intent, the execution spec and the result; RunState binds those **artifacts** by digest or
    reference, never the values.
  Each derivation is validated where it happens, which is what keeps this from being the TURN-216
  defect: that bug was two encodings for one field with no checked relationship, whereas each of these
  is a source representation and a derived one with a checked derivation between them.
- **Windows environment names are case-insensitive, and the digest must agree with the OS (TURN-240
  pin 2).** `Path` and `PATH` are one variable to Windows but two entries to a sorted list, so a
  digest could bind two entries while the OS supplies one. Identity is defined by an **upper-case
  fold** applied **before** dedup, sort and digest. Two allowlisted names that collide under the fold
  are **rejected at attach**, naming both spellings — the allowlist is operator-authored, so a
  collision is a mistake to fix rather than a precedence puzzle to resolve silently. Unix keeps
  byte-exact name identity, since names there are case-sensitive.
- **Base64 preserves bytes; it does not make them a valid environment (TURN-241 pin 2).** A decoded
  pair still has to form an unambiguous `name=value` and still has to survive `execve`, so the grammar
  is validated **before persistence and before execution**, not merely round-tripped: a name may not
  be **empty** and may not contain **`=`** or **NUL**; a value may not contain **NUL**. Without this,
  a canonical spec could decode to something that cannot be reassembled unambiguously, or that the
  kernel rejects after the digest already authorized it.
- **Names are restricted to a portable ASCII grammar, which is what makes the Windows fold exact.**
  `[A-Za-z_][A-Za-z0-9_]*`. An abstract "upper-case fold" was not a specification — Windows
  case-insensitive comparison is locale- and API-dependent, and validation and child-environment
  construction must agree **exactly** or the digest binds entries the OS block does not contain.
  Restricting names to ASCII makes the fold a plain `A-Z` mapping, identical in both places, and
  removes the non-ASCII case-pair question entirely rather than answering it. Non-conforming names are
  refused at attach, naming the variable. Unix keeps byte-exact name identity; Windows folds before
  dedup, sort and digest.
- **Required vectors:** an inherited Unix value containing invalid UTF-8, surviving unchanged to the
  child; a mixed-case Windows allowlist (`Path` + `PATH`) refused at attach; `env.set` entries with an
  empty name, a `=` in the name, a NUL in the name and a NUL in a value, each refused; and a
  non-ASCII name refused.
- It is delivered on a dedicated **`spec` pipe**, read to EOF before `READY`, under its own explicit
  size ceiling. It is a stream, not a frame, because the frozen environment can exceed the `PIPE_BUF`
  frame bound — and conflating the two would have quietly capped the environment at 4 KiB.
- **The transfer is inside the arming deadline and is INTERRUPTIBLE (TURN-240 pin 3).** A spec larger
  than pipe capacity plus a supervisor that never reads it would block the coordinator's write
  indefinitely — and a blocked coordinator cannot run the very deadline that is supposed to bound
  arming, so the run guard would be held forever. That is the unbounded-under-guard hole from TURN-237
  pin 2, reopened by the channel added for TURN-239 pin 2: a fix for one round reintroducing an
  earlier round's defect through a new path.
  The **write, read and validate sequence shares the one fixed arming deadline**, and the write is
  implemented so the deadline can actually fire: a deadline-aware `*os.File` (`os.Pipe` files are
  registered with the runtime poller, so `SetWriteDeadline` works on them), or a separately
  cancellable writer whose FD is **closed and joined** on expiry — never a bare blocking write on a
  goroutine nobody can stop. Expiry takes the §1 arming-failure path: no `READY`, no CAS, no attempt.
  **Test:** a supervisor that accepts the inherited FDs and then **never reads `spec`**, proving the
  deadline fires and the guard is released.
- **Not argv, and not the supervisor's environment.** Passing it as internal CLI arguments or by
  launching the supervisor with the child's environment would expose it through `/proc/<pid>/cmdline`
  and `/proc/<pid>/environ`, and would make "the child's environment" and "the supervisor's
  environment" the same object — so the obligation below could not even be stated, let alone tested.
- **Not written into the attempt root either — for the narrower reason that is actually true
  (TURN-240 pin 4).** An earlier draft justified this as avoiding an on-disk exposure "otherwise
  avoided", which contradicts this same document: `ResolvedExecution` persists the **actual** resolved
  values in the `BootstrapIntent` and in RunState v8. The values are already on disk, by design, in
  one place with one lifetime. What the pipe avoids is an **additional attempt-local copy** — another
  location holding the same values, with its own cleanup and its own failure modes. That is a real
  benefit and it is the only one claimed.
- **Validated before `READY`**, so a bad spec never reaches the CAS: digest equal to the one bound in
  the intent, executable path absolute and equal to the **`ResolvedCommand` bound in that intent**
  (§2 — resolution happens at attempt start, so there is no attach-time path to compare against), argv
  non-empty, cwd equal to the run worktree, environment within the §2 ceilings. The expected digest is not taken on trust from
  the sender — the supervisor reads `intent.v1.json` **through the attempt directory FD** it already
  holds, which is durable before arming begins (§5 step 2 precedes step 3) and rooted rather than
  name-resolved. Any failure means no `READY`, which the
  coordinator's bounded arming path already turns into a refusal with no attempt bound.
- **The obligation is exactness, and it is testable:** the child's environment is built **only** from
  the spec — never `os.Environ()`, never the supervisor's own — and no internal routing state (attempt
  id, FD numbers, the internal route marker) is added to it. The test asserts the child's observed
  environment equals `ResolvedExecution` and argv equals `ResolvedCommand` **byte for byte**,
  including empty argv elements and including the absence of anything the supervisor carries.

**Arming is bounded, and its failure path is defined (TURN-237 pin 2).** Arming happens under the run
guard, so a wedged or malformed supervisor would otherwise hold the **shared** guard indefinitely —
precisely the unbounded-inside-the-lock property this gate exists to avoid. The arming handshake
(spawn → `READY`) therefore carries a **short fixed deadline**. On spawn failure, handshake failure,
deadline expiry, or lease-acquisition failure the coordinator: closes its `ctrl` write end so the
supervisor sees EOF and cleans up; reaps the supervisor; confirms **no command was enabled** — which
is structural rather than observational, since `GO` is the only thing that starts a command and `GO`
is sent only after the CAS; then releases the guard **with no active CAS**, so no attempt is bound and
no ledger entry exists.

If that cleanup is itself ambiguous — the supervisor cannot be reaped, or its state is unknown — the
coordinator returns the typed **recovery-required** error. It does not release the guard while leaving
an unaccounted helper behind, and it does not downgrade to a best-effort claim.

**Command surface and authorization (TURN-234 pin 5).** The supervisor mode is a dispatchable route,
so it is enumerated — concealing it would be precisely the unenumerated-route defect found in the
alias namespace at TURN 224. But "an internal marker and a live parent" is **not a capability**: every
caller can pass a marker and every process has a parent. Corrected:

- A separately enumerated **internal process-mode namespace**, excluded from ordinary help and from
  the agent-facing verb set, but **included in the route-exhaustiveness invariant** so the surface
  test still enumerates every dispatchable route.
- Authorization is an **inherited-handle handshake**: the parent passes an inherited pipe/handle and
  the child must read from it. An unrelated caller cannot inherit that handle, so the capability is
  unforgeable rather than declared.
- **The ordering is pinned, because one cut is not enough (TURN-235 pin 2, re-based at TURN-236 pin
  1).** "Pipe closed before the `GO`" was the only race covered, yet a `GO` may already be
  **buffered** when the parent dies, so the read succeeds and the supervisor could spawn parentless.
  The earlier fix ordered `PR_SET_PDEATHSIG` first; since that primitive is thread-scoped and unsound
  here, the ordering is re-based on the channel itself. The supervisor, in order: (1) installs the
  catchable cleanup signal handler; (2) begins monitoring the inherited `ctrl` read end for **EOF**,
  which is armed by inheritance rather than by a syscall and therefore cannot be raced — a death that
  happened before the supervisor ran leaves EOF already pending; (3) sets `PR_SET_CHILD_SUBREAPER`;
  (4) sets `FD_CLOEXEC` on the inherited attempt directory FD, acquires the lease by `openat` on it,
  and reads and **validates the execution spec** — it does **not** create the owned command group, see
  below; (5) sends **`READY{challenge}`** on `stat`; (6) receives **`GO{challenge}`** on `ctrl` and
  refuses any other value; (7)
  re-checks that `ctrl` is still open and retains it through spawn, so a buffered `GO` from a dead
  parent starts nothing; (8) sets `FD_CLOEXEC` on the `ctrl` read end and the `stat` write end —
  **retaining both**, since it needs them for death detection, `CANCEL` and `TERMINAL` — and spawns
  the command with `Setpgid`, closing its own stream write-end copies immediately after a successful
  `Start` and on every failure path.
- **The supervisor and the owned command group are two DIFFERENT identities (TURN-238 pin 2).** An
  earlier draft had the supervisor establish "its own process group" while dormant, and cleanup then
  killed `-pgid` — which would have killed the only process able to reap the group and publish the
  receipt. The supervisor therefore stays **outside** the owned group. After `GO` it creates the
  command leader with `setpgid` in the fork/exec setup, so the child is the leader of a **fresh**
  group before any user code runs. Only that **command PGID** is signalled, group-waited and written
  to the receipt, and it cannot exist before the command does — so a **no-command receipt carries no
  command PGID**, which is also how recovery tells the two receipts apart.
- **Test:** kill the parent at **each** handshake and launch cut on the shipped path — including
  *after the `GO` write but before spawn*, and *after arming but before the active CAS* — and prove
  either that no command starts, or that the owned containment domain is cleaned; in both cases the
  receipt must be published, with `command_started` recorded truthfully.
- It receives **bounded handles and identities**, never caller-chosen authoritative paths.

**The terminal sequence is ordered, on EVERY path (TURN-238 pin 3).** The reap-before-return rule was
phrased only for timeout and cancel, and the components — receipt, `TERMINAL`, lease release,
coordinator finalization — were each defined without an order between them. That gap lets a valid exit
frame race ahead of the proof that no background descendant remains, so the coordinator could finalize
a **pass** while a grandchild is still writing to the worktree. Normal exit and spawn failure are
included, not just the interesting paths.

Supervisor, in order, on every terminal path:

1. close its own stream write-end copies, so the coordinator's stream EOFs can arrive;
2. drain, kill and group-reap the owned command group as applicable (§ above, `waitpid(-pgid)`
   iterating to `ESRCH` under the cleanup deadline);
3. **publish the cleanup receipt through the retained attempt directory FD** — rooted (never a
   path re-resolved by name), **no-clobber**, canonically encoded, and **durability-confirmed**
   before it counts as published;
4. send **exactly one** `TERMINAL`, and only after that confirmation;
5. release the lease, close the attempt directory FD, close `stat`, exit.

**The receipt authority is what makes steps 3 and 5 mean anything (TURN-239 pin 4).** "Durably
publish" was an unspecified verb sitting between two precise ones. The retained directory FD is
exactly the resource that lets publication be rooted rather than name-resolved, and the lease is what
makes the publisher the authoritative one — so both are held *through* step 3 and released only in
step 5, never earlier.

Fail-closed on the same rule recovery uses: a **receipt conflict** (one already exists), a
**malformed pre-existing receipt**, or **post-commit durability ambiguity** each mean **no successful
terminal is sent** and the attempt **BLOCKS**. A cleanup-deadline expiry is the same. The supervisor
exits with the proof absent, which is the state recovery is already specified to refuse — rather than
a second, weaker path that lets an unproven cleanup look finished.

Coordinator: drain both streams **concurrently** — draining them in sequence deadlocks the moment the
other pipe fills — and publish `result.v1.json` or apply an outcome only once the well-formed
`TERMINAL`, the cleanup fact, both stream EOFs and the supervisor reap **all agree**. Any disagreement
is recovery-required, not a tie broken in favour of the frame.

On timeout/cancel the coordinator sends **`CANCEL`** on `ctrl`; the supervisor kills the whole owned
command group and then runs exactly the sequence above — a returned-but-unreaped tree is
indistinguishable from a live one. `CANCEL` is a **stop request, not a fact**: `TERMINAL`
still reports what actually happened, so a command that had already exited zero before the frame
arrived is reported as having exited zero, and the coordinator (which knows whether it sent `CANCEL`
for a timeout or for an operator cancel) resolves the outcome under §7, where cancel outranks timeout.
Timeout and cancel share one frame because the supervisor's job is identical in both cases; the reason
never leaves the coordinator, so a supervisor cannot invent one.

There are consequently two cancel mechanisms with one authority, and the relationship is stated so it
is not mistaken for redundancy: **`cancel.requested` on disk is the durable operator fact** (§6), and
the coordinator that observes it is what turns it into a `CANCEL` frame. The supervisor never reads
the cancel file — it has no authority to interpret operator intent, only to stop what it owns.

`cmd.Env` is **non-nil**, built from the frozen policy (§2); `cwd` is the run worktree — a fixed
directory, **not** confinement: the child holds the user's OS authority.

**Tests:** surviving grandchild; timeout; explicit cancel; spawn failure; and **killing the parent
coordinator process itself** — exercising the **actual shipped supervisor path**, not a test-only
helper production cannot launch. On a platform with no proof, the test asserts recovery *blocks*
rather than passing vacuously.

## 2. Run-policy v2 (D016 amendment)

`test_gate` is **exactly one of** `disabled: true` **or** non-empty `argv`. No implicit shell — a
shell must be named (`["sh","-c","…"]`).

```jsonc
"test_gate": {
  "argv": ["go", "test", "./..."],          // XOR "disabled": true
  "env": { "inherit": ["PATH"], "set": {} } // see below
},
"limits": {
  "test_timeout_seconds":     1800,
  "max_test_attempts":        20,      // NEW: ledger ceiling; 0 < n <= config.MaxBudget
  "max_test_output_bytes":    32768,   // NEW: combined RETAINED excerpt, RAW bytes
  "max_test_record_bytes":    65536    // NEW: CANONICAL-byte ceiling of result.v1.json
}
```

**Bounds must be cross-validated, not merely present (TURN-233 pin 3).** The result is issued to the
verifier as an evidence-packet file, so a policy-valid record that cannot be packetized would be a
policy that permits an unissuable run. Validation requires:

`max_test_record_bytes <= evidence_max_file_bytes <= evidence_max_total_bytes`

with defaults chosen to satisfy it (65536 <= 98304 <= 262144). `max_test_attempts` must be positive
and bounded by the shared storage ceiling `config.MaxBudget`, since every entry lands in a
full-snapshot RunState.

**Canonical expansion is bounded by construction.** Retained excerpts are **base64**, so encoding
expands by exactly 4/3 and the worst case is arithmetic rather than a guess — JSON string escaping of
arbitrary control bytes could otherwise expand ~6x and silently exceed the ceiling.

**But shrinking the excerpt is not sufficient (TURN-234 pin 4).** The record's authoritative metadata
is VARIABLE, not a fixed allowance: the VERIFY contract requires the exact argv, and the environment
identity is bound too. A long argv or a large environment identity can consume the ceiling before a
single output byte is encoded, so a **zero-output** result could exceed it with nothing left to shrink
— discovered only after the command had already run.

So the fit is proven at **attach**, not at record construction:

- At first attach, compute the worst-case canonical size of the fixed record for THIS run — the frozen
  argv, the frozen environment identity, and every fixed field at its maximum encoding — and require
  `fixed_worst_case + minimum_excerpt_reserve <= max_test_record_bytes`.
- A policy that cannot satisfy that is **rejected at attach**, with remediation naming which component
  is too large. A run therefore never reaches TESTS carrying a command whose result would be
  unissuable.
- Record construction then only ever shrinks the EXCERPT, against a budget already proven to exist.

**Attempt-time executable resolution reopened this proof, so the bound covers it (TURN-242 pin 2).**
Moving resolution to attempt start (§2) made the result carry a base64 absolute executable path whose
**selected value is unknown at attach** — so a policy could pass the attach fit and then produce a
**zero-output** result that exceeds `max_test_record_bytes`, which is exactly TURN-234 pin 4 recreated
through a new path. The same shape as TURN-240 pin 3: a fix for one round defeating an earlier round's
fix.

The attach-time worst case therefore includes a **proven maximum for the resolved path**, which is
computable because the candidate set is finite and frozen:

- for a **separator-bearing** `argv[0]`, the single candidate — the run worktree cwd joined with it,
  cleaned;
- for a **bare** `argv[0]`, the maximum over every frozen `PATH` entry (relative and empty entries
  made absolute against that cwd) joined with `argv[0]`, times every `PATHEXT` suffix on Windows;
- the reserve is that maximum's **base64 worst case**, `4*ceil(n/3)`, not its raw length.

Belt and braces, because a proven bound that is never re-checked is a belief: **actual fit is
re-checked at attempt start, before the intent is published and before arming**, and exceeding it is a
typed **pre-execution refusal** — no intent, no attempt, nothing bound. A near-ceiling policy whose
**longest** `PATH` candidate is the one selected is a required vector.

- `argv[0]` nonblank; NUL rejected anywhere; intentionally **empty later arguments preserved**;
  secrets rejected in every executable/control element.
- **Environment is frozen at attach, in a SEPARATE shape (TURN-234 pin 3).** Naming an ambient
  variable makes inheritance intentional but does not freeze its VALUE, and identity binding would
  only detect drift *after* it had already changed execution. But resolving values INTO
  `EffectivePolicy` would break a durable invariant that already exists: `BootstrapIntent` requires
  `reflect.DeepEqual(ParseRunPolicy(PolicyCanonical), EffectivePolicy)`
  (`internal/attach/intent.go:83-85,201-208`). Two shapes, not one:
  - `EffectivePolicy` — **unchanged**, exactly `ParseRunPolicy(PolicyCanonical)`; the existing
    equality invariant survives untouched.
  - `ResolvedExecution` — **new persisted field**: the allowlisted environment resolved once at first
    attach, plus the scratch HOME/cache/temp paths. **Not argv and not the executable** — those are
    `ResolvedCommand`, produced per attempt (below). Attempts AND **recovery** take the environment
    only from this field, so nothing re-reads ambient values after bootstrap and a recovered attempt
    cannot silently execute in a different environment than the one authorized.
  - A durable required-field change, so `bootstrapIntentVersion` bumps, with validation that every
    resolved name is in the source allowlist.
  - **Durable authority path (TURN-235 pin 5).** `ResolvedExecution` is written into the
    `BootstrapIntent` and, on completion, **bound into RunState v8**; later attempts and recovery read
    the STATE-bound copy, never re-deriving it and never re-reading the journal. Its validation is
    immutability: the state-bound value must equal the completed intent's exactly.
  - **Bounded before journaling.** Inherited values are not bounded by the 16 KiB policy source, while
    a txn intent payload is capped at 64 KiB (`internal/txn/txn.go:51,573-574`). So the resolved
    environment carries explicit ceilings — maximum name count, maximum per-value bytes, and maximum
    aggregate canonical bytes — validated at attach, before anything is journaled. Exceeding them is
    an attach-time refusal naming the offending variable.
- **`HOME` is NOT inherited by default.** Common tools auto-load credential-bearing Git/npm/cloud
  config from it, which would have contradicted this same contract's "no provider token". The default
  allowlist is the minimal execution set only — `PATH`, plus `SystemRoot`/`ComSpec` on Windows — and
  the run supplies a **tool-owned per-run scratch `HOME`/cache/temp** pointing inside the run
  directory. Anything more must be named explicitly by the operator.
- **Freezing `cmd.Env` does NOT freeze executable lookup (TURN-235 pin 4).** `exec.Command` resolves a
  name containing no path separator via `LookPath` **when the command is constructed** — before
  `Cmd.Env` is assigned — so it consults the COORDINATOR's ambient `PATH`. The frozen environment
  could authorize one `PATH` while a different ambient one chose the binary. Lookup is therefore
  performed explicitly against the **frozen** `PATH`/`PATHEXT` (`PATHEXT` is added to the Windows
  allowlist, which previously omitted it) rather than an ambient one.
- **Resolution happens at ATTEMPT START, not at attach — and `ResolvedExecution` does not carry the
  executable (TURN-241 pin 1).** A later section had begun treating `ResolvedExecution` as though it
  also carried argv and the resolved executable path, which gave one persisted field **two
  incompatible shapes**. Worse, resolving at attach is not generally possible: a workspace-relative
  test executable such as `./scripts/test` **may not exist when the worktree is provisioned**, because
  the accepted implementation commit can create it afterwards. An attach-time resolution would fail on
  a perfectly valid policy, or bind a path that later changes meaning. The split, stated once:
  - **`EffectivePolicy`** keeps the **source argv**, unchanged and plain, preserving the existing
    parse-equality invariant.
  - **`ResolvedExecution`** is frozen **at attach** and holds the resolved **environment** and the
    scratch `HOME`/cache/temp paths — and nothing about argv or the executable.
  - **`ResolvedCommand`** is produced **at attempt start, under the run guard**, with the **run
    worktree as cwd**. The selected **absolute** path plus the argv array are bound in the **attempt
    intent, the execution spec and the result**.
  - **The resolution algorithm, completely (TURN-242 pin 3).** An earlier draft specified only the
    `PATH` search — and then used `./scripts/test` as its motivating example, which is precisely the
    case that search never applies to:
    1. **`argv[0]` containing a path separator resolves DIRECTLY against the cwd, never through
       `PATH`.** That is the motivating case, and routing it through a search would find a different
       binary or none.
    2. A **bare** `argv[0]` uses the frozen `PATH`/`PATHEXT` search, honouring **relative entries**
       (resolved against that cwd) and **empty entries**, which mean the current directory.
    3. The selected path is made **absolute and cleaned**, then must satisfy the platform's
       executable-file rule: on Unix a **regular file** — reached through symlinks if any — with
       execute permission for the effective user; on Windows an existing file whose extension is in
       `PATHEXT`, or an exact-name match. A **directory** or a non-executable candidate is not a hit
       and the search continues.
    4. The **exact chosen path is recorded** — the path handed to exec, not a resolved symlink target.
       Recording the target would claim something about an inode the design cannot hold across the
       TOCTOU window; the chosen path is what actually ran.
  - **Failure timing and classification.** Lookup, permission and type failures happen **before the
    intent is published and before arming**, so they are a typed **pre-attempt policy refusal**: no
    attempt minted, no ledger entry, no budget consumed, and **not** `spawn_failed`, since no attempt
    exists to carry an outcome. `spawn_failed` remains reachable and remains authoritative for its own
    case — resolution succeeded at attempt start and `exec` nevertheless failed after `GO`, e.g. the
    file was removed in between.
  - The supervisor therefore validates against the **intent/spec digest**, never against an
    attach-time executable field that does not exist.
  - **Required vectors:** a workspace-relative executable **generated by the accepted commit** (absent
    at attach, present at attempt start) with `PATH=.`, proving both the timing and the empty/relative
    entry semantics; a **direct relative** `./scripts/test` proving `PATH` is not consulted; a
    candidate that is a **directory**; a candidate that exists but is **not executable**; and
    **not-found**, each refused before any attempt is bound.
- **Secret-bearing values are REJECTED, not redacted — with an honest scope (TURN-235 pin 5).** Every
  resolved inherited value and every `env.set` value is checked before it is persisted or executed,
  and rejection (rather than redaction) is what lets the frozen environment be bound by a digest over
  its **actual** values: redacted pairs collapse distinct secrets onto one marker, so such a digest
  could not prove equality.
  **What this does and does not claim.** `internal/redact` states plainly that its detection is
  heuristic and does not catch every secret, so "the frozen environment is secret-free" would be an
  overclaim. The real guarantees are: (a) **allowlisting** — an operator naming a variable authorizes
  persisting its value, and nothing unnamed is ever read; (b) **rejection and the no-raw-bytes-on-disk
  rule cover the enumerated token families** in the detector plus schema-sensitive variable names.
  Anything outside those families that an operator explicitly allowlists is authorized by that act,
  not certified absent.
- `RunPolicyVersion` → 2. A v1 document is **refused**, never reinterpreted.
- **Parse-order fix:** `ParseRunPolicy` today probes only for the *presence* of `schema_version` then
  `strictDecode`s the v2 shape before comparing versions (`internal/config/config.go:229-253`), so a
  v1 policy carrying `command` fails with an unknown-field error instead of version remediation. The
  probed version must be compared **before** the strict decode.

## 3. On-disk shapes

Per-run attempt root `<run>/tests/<attempt_id>/`:

| Leaf | Written | Meaning |
|---|---|---|
| `intent.v1.json` | before the active CAS | immutable: attempt id, the attempt's **`ResolvedCommand`** (argv + the absolute executable resolved at attempt start), cwd, **effective env identity**, the **`exec.spec.v1` digest** the supervisor must match (§1), frozen policy bounds, tested commit/tree, start revision |
| `result.v1.json` | **inside the final guarded section**, after the final identity observation | the one immutable canonical record; the digest state binds |
| `stdout`, `stderr` | during the run | bounded, **redacted** retained excerpts |
| `cancel.requested` | any time | durable, idempotent, rooted, no-clobber, durability-confirmed |
| `lease` | held while running, and **through cleanup** | OS-held; held ⇒ live owner, unheld ⇒ owner died |
| `cleanup.receipt.v1.json` | by the supervisor, before releasing the lease (Linux) | the durable completion fact recovery requires; absent/ambiguous ⇒ BLOCK |

**Effective environment identity.** Intent and result bind the sorted variable **names** plus a digest
over the canonical **actual** name/value list — not a redacted one. Redacted pairs collapse distinct
secrets onto one marker, so a redaction-based digest cannot prove equality. An earlier draft said
"redacted" here and "actual" elsewhere; **actual** is the rule.
Both names and values enter that digest **base64-encoded** and, on Windows, **upper-case folded and
dedup-checked first** (§1, TURN-240 pin 2) — otherwise the digest binds bytes the OS never supplies.
The §2 per-value and aggregate ceilings are measured on **raw bytes, before encoding**, so the wire
encoding cannot silently move a limit.
The justification is the scoped one from §2, not the absolute one an earlier draft stated here
(TURN-236 pin 4): the frozen environment holds only **operator-allowlisted** names, and values
matching the detector's enumerated token families are **rejected** at attach. It is not claimed to
"contain no secrets to leak" — `internal/redact` documents its detection as heuristic, so a value
outside those families that an operator allowlisted is authorized by that act, not certified absent.

**Streams — representation pinned for arbitrary bytes (TURN-233 pin 4).** Process output is
arbitrary bytes; the harvested vectors explicitly include non-UTF-8 raw streams.

- The `stdout`/`stderr` leaves are **non-authoritative crash-time staging**: partial evidence retained
  for an interrupted attempt, never the thing state binds.
- The **immutable result embeds the exact retained representation** as **base64**, so the record is
  self-contained and lossless for invalid UTF-8.
- It binds, separately and unambiguously. "Raw byte counts BEFORE encoding" was **not a definition**
  (TURN-236 pin 5): the digest covers the redacted stream, the retained counts cover a redacted
  excerpt, and redaction **changes length** — so "before encoding" left open whether the count was of
  process bytes or of redacted bytes, and a producer and a verifier schema could have agreed
  syntactically while attesting different quantities. Named apart:
  - `stdout_source_bytes`/`stderr_source_bytes` — bytes read **from the process**, before redaction.
  - `stdout_redacted_bytes`/`stderr_redacted_bytes` — bytes of the **full redacted stream**, which is
    the stream the digest covers. These differ from the source counts whenever a replacement differs
    in length from the token it replaced.
  - `stdout_sha256`/`stderr_sha256` over the **entire redacted stream**, computed streaming.
  - `stdout_retained_b64`/`stderr_retained_b64`, their retained byte counts — of the **redacted**
    excerpt — and `truncated` flags for the bounded excerpt actually kept, under a deterministic
    **head+tail with an explicit elision marker** rule within `max_test_output_bytes`.
  A required vector emits a secret whose replacement length differs from the matched token and asserts
  `source_bytes != redacted_bytes`, that the digest matches the redacted stream, and that the excerpt
  ceiling is applied to redacted bytes. Without a length-changing vector the two counts can be
  conflated and every test still passes.

**What the verifier can RECOMPUTE vs what the runner ATTESTS (TURN-235 pin 7).** The record retains a
bounded excerpt, so "the verifier recomputes every fact" was too strong — it cannot recompute a digest
over a stream it does not have. The boundary, named so the evidence claim stays auditable:

- **Recomputable from the record alone:** canonical encoding and the record digest; the retained
  excerpt's own bytes, counts and truncation flags; the bound argv, resolved executable path,
  environment identity, and tested commit/tree.
- **Runner-attested, not recomputable:** the full-stream **source and redacted** byte counts and the
  digests over the entire redacted streams. They are facts the runner observed while streaming and are trusted at the same
  level as the exit code — which is the honest framing, since nothing else saw the full stream.

**Redaction precedes every write.** Redaction happens in the streaming path *before* any write,
including to the staging leaves, so no byte matching the detector's enumerated token families reaches
disk in raw form. Stated with its real scope (TURN-236 pin 4): this is **not** "no secret-bearing
bytes reach disk". Detection is heuristic and bounded by those families, and implementation and tests
must encode the scoped claim so the absolute one is not accidentally re-adopted downstream.

**The chunk-boundary guarantee needs a bounded-memory streaming STATE MACHINE, not an overlap window
(TURN-234 pin 2).** An overlap of "at least the longest matchable token" is unimplementable here,
because the token language has **no longest token**: `internal/redact/redact.go` uses unbounded tails
throughout — `{6,}`, `{16,}`, `{20,}`, `{10,}`, the bearer value, and the key/value value.

**Nor is every prefix bounded (TURN-235 pin 3).** An earlier draft claimed a finite longest-prefix
window; that is also false. The bearer prefix is `bearer` + an unbounded whitespace run, and the
key/value prefix contains **two** unbounded runs (`\s*[:=]\s*`). A window sized to "the longest
prefix" does not exist either.

What is bounded is the **state**. The redactor is an incremental DFA:

- whitespace inside a candidate prefix is consumed **in state** and emitted as it goes — it is not
  secret, so it need not be buffered, and the candidate survives arbitrarily long runs;
- minimum-length token families (`{6,}`, `{10,}`, `{16,}`, `{20,}`, the fixed-width AWS id) use
  **bounded lookahead equal to that minimum**, which is finite; a candidate that ends below the
  threshold at a delimiter or EOF is **flushed unchanged**, because it was never a match;
- on a confirmed match the placeholder is emitted **once** and continuation bytes are consumed without
  buffering;
- idempotence holds — an already-emitted placeholder is not re-redacted.

Memory is bounded by the largest minimum-length threshold, not by the longest prefix and not by the
longest secret.

**The correctness obligation is equivalence, not inspection:** the streaming redactor must produce
**byte-for-byte identical output to whole-buffer `redact.Bytes`** over randomized chunkings of
randomized inputs. That is the property worth testing, because it cannot be satisfied by a plausible
looking state machine that merely passes hand-written cases. It is its own tested unit: the "no secret reaches disk" claim
rests entirely on it. **Vectors:** an arbitrarily long token; a delimiter arriving many chunks later;
EOF mid-token; a prefix split across a chunk boundary; idempotence over already-redacted input.

## 4. RunState v8 (TURN-231 pin 1, TURN-232 pin 2)

A store alone is insufficient: `SubmitTestOutcome` is non-idempotent and delegates replay identity to
a future journal, and `engine.Apply` records no TESTS source (`internal/engine/engine.go:612-620`), so
RunState has no attempt identity at all.

- `ActiveTestAttempt *TestAttemptRef` — at most one. Binds attempt id, start revision, tested
  commit/tree, intent digest, and a **`CancelPending bool`**.
- `TestAttempts []FinalizedAttempt` — **append-only**; binds attempt id, start/bound revision, tested
  commit/tree, canonical result digest, execution + identity outcome, terminal reason, and resulting
  revision.

**Invariants.**
- At most one active ref.
- The ref may exist at **ownerless TESTS**, *or* in a **cancelled lifecycle awaiting terminal
  binding** (`CancelPending`). This is what lets 05.7 mark `LifecycleCancelled` immediately so
  `status`/`wait` wake, without discarding the only identity the runner can finalize. The previous
  "non-TESTS has no active ref" rule would have rejected that state.
- State references an intent or result **only after** the canonical record is durably published and
  re-confirmed.
- A result digest already in the ledger cannot authorize a second, differing outcome.
- `len(TestAttempts) <= max_test_attempts`.

**Two finalization shapes (pin 2).**
- **Outcome finalization** — `pass`/`fail`: atomically moves the exact active ref into the ledger
  **and** applies the TESTS edge, in one CAS.
- **Ledger-only finalization** — `cancelled` / indeterminate: atomically clears the active ref and
  appends the ledger entry, applies **no** edge, leaves the test budget untouched, and leaves the run
  explicitly retryable (ownerless TESTS) or cancelled.

**Cancel vs result race.** Both CAS under the run guard, so one is first. If cancel binds first the
attempt becomes `CancelPending` and the runner's subsequent finalization is a **ledger-only
`cancelled`** binding — the result is still bound as evidence, never discarded. If the result binds
first, the cancel is a no-op against a finalized attempt.

**Attempt exhaustion (pin 5d).** Indeterminate retries are deliberately **not** limited by
`TestFixes` — the code did not fail. Without a ceiling they would grow a full-snapshot RunState
without bound, so `max_test_attempts` halts the run for operator action with a typed
`ErrTestAttemptsExhausted`. Repeated indeterminacy means the environment is broken; classifying it as
a code test failure would be a lie that also burns the fix budget.

## 5. The lifecycle machine (TURN-232 pin 1 — corrected order)

1. **Under the run guard:** authorize exact ownerless TESTS **and no active attempt**; freeze the
   latest accepted commit/tree and the policy; prove exact identity (registered run branch / HEAD /
   commit / tree / index / worktree); derive `ResolvedCommand` (§2) and **re-check record fit** —
   both before anything is minted, so a resolution or fit failure is a pre-attempt refusal that binds
   nothing; then mint and lock one attempt.
2. Durably publish the immutable **intent**.
3. **Arm the containment DORMANT** (§1 launch ordering, TURN-236 pin 2): on Linux spawn the
   supervisor and complete the handshake so it holds the lease and the receipt authority while
   blocking on **GO**; on Windows create the **unnamed** job and hold its sole handle. **No command exists
   yet**, and from here on every state carrying an active ref also has a live receipt authority.
4. **CAS-bind** `ActiveTestAttempt`.
5. **Release the run guard.**
6. **Send GO** — only now does the command spawn, inside already-armed containment.
7. Execute while holding the per-attempt **OS lease**. The subprocess is entirely outside the lock.
8. **Reacquire the run guard.**
9. Re-authorize the exact active attempt; perform the **final exact identity observation**.
10. Construct and durably publish the **one canonical result** — it can now truthfully freeze
    `unchanged` vs `changed`, which it could not before step 9.
11. **CAS the outcome into state**, then release the guard.

Publishing the result *before* the final locked observation (the TURN-231 order) was wrong: the record
is immutable and contains the identity distinction, so it cannot be written before the fact it
asserts exists. Only bounded record publication is inside the lock; the subprocess never is. Arming
before the CAS is the same kind of correction in the other direction: a durable fact recovery depends
on must exist before the state that obliges recovery to read it. This also
**serializes a late operator-cancel against outcome finalization**.

**Concurrency.** Active + **held** lease ⇒ report the same running attempt, never start another.
Active + **unheld** lease ⇒ the owner died.

**Orphan policy (no rerun).** A possibly side-effecting command is never re-run automatically. The
orphan terminalizes `interrupted` with partial evidence retained, requires an explicit **new**
attempt, and does not consume the test-fix budget. Recovery must **prove no process remains in the owned containment domain** — the completion fact of
§1, not a claim about escaped descendants
(§1) before permitting another attempt; where the platform cannot prove it, recovery blocks.

## 6. Trigger and cancel

**No new agent-facing verb.** The `submit` orchestration that durably enters TESTS starts or resumes
the gate **after releasing the acceptance guard**; accept-once replay/recovery covers a crash in the
enter-TESTS → bind-active gap. The active ref keeps `status` lock-free and coherent and lets a second
invocation report *already running*.

`cancel.requested` is durable, idempotent, rooted, no-clobber and durability-confirmed; the
**coordinator** polls it **outside** the run lock and, on observing it, sends the `CANCEL` frame (§1).
The supervisor never reads the file: interpreting operator intent is not its authority. Operator cancel terminalizes `cancelled` and **never routes
TESTS→FIX** — nobody's code failed. A **caller context disappearing** is not an operator decision: it
is `interrupted`/indeterminate under the orphan policy, retryable, budget untouched.

## 7. Outcome mapping (TURN-232 pin 5e) — separate execution and identity

Overlapping facts are removed by construction rather than by a precedence list: the record carries two
independent fields, and the outcome is a total function of the pair.

`execution` ∈ `ok | nonzero | timeout | cancelled | spawn_failed | interrupted`
`identity` ∈ `unchanged | changed | unobserved`

| execution | identity | outcome |
|---|---|---|
| `cancelled` | any | **cancelled** — ledger-only, no edge, no budget |
| `spawn_failed`, `interrupted` | any | **indeterminate** — retryable, no budget |
| any | `unobserved` | **indeterminate** — the gate cannot decide what it cannot observe |
| any | `changed` | **fail** |
| `timeout` (`exit_code: null`) | `unchanged` | **fail** — ordinary test-failure edge |
| `nonzero` | `unchanged` | **fail** — ordinary test-failure edge |
| `ok` (exit 0) | `unchanged` | **pass** |

Cancel outranks timeout: operator intent supersedes a bound. `disabled: true` produces a durable
no-process result (`execution: ok`, `terminal_reason: "disabled"`) with the **same exact commit/tree
proof**, and is admissible **only when the task declares no required tests**.

## 8. The tested-tree obligation and the phase-graph ruling

Identity is proven at attempt **start** and again at **final observation** (§5 step 9), the successful
observation being the external-filesystem linearization point. The passed attempt's commit/tree is
retained in the ledger and **re-proven on the verifier submit, immediately before VERIFY→DONE** —
proving it only when tests finish still lets a clean `reset --hard` land afterwards.

**The non-adversarial hole.** A VERIFY failure routes its FIX back **directly to ownerless VERIFY**
(`internal/engine/engine.go:433-456`), so that fix produces a new accepted commit *after* the last
passed attempt and no tests rerun. Two agents behaving correctly reach it.

**Ruling (CX TURN 232), adopted:** in `evalFixImplemented`, `FixReturn == VERIFY` routes to **TESTS
via the existing `RouteToTests`**. No new edge and no gate-only special case — the edge predicate
already admits `FIX → TESTS` (`engine.go:1038-1040`), and every TESTS pass already enters ownerless
VERIFY with a freshly computed pair-generation threshold. That yields VERIFY-fix → TESTS → VERIFY with
**one** edge table. Engine, materialization, and E2E tests update accordingly.

**Verifier evidence (TURN-232 pin 4).** The VERIFY packet currently carries task, agreed plan and
cumulative changed files only (`internal/reviewpacket/phases.go:112-123,221-242`). A ledger entry
makes the pass auditable *internally*, but the fresh verifier must be able to inspect **which argv
ran**, the exit/timeout facts, truncation and output digests. So the VERIFY packet gains the exact
canonical passed `result.v1.json` at a reserved context path, re-verified from the store by attempt
id + digest, counted against packet bounds. Disabled results appear too. **Removing that resolver
entry must fail a mutation test.**

## 9. Crash / TOCTOU table (corrected order)

| Cut | Durable residue | Recovery |
|---|---|---|
| before intent published | nothing | fresh attempt |
| after intent, before arming containment | orphan intent, no state ref, nothing spawned | orphan ignored; fresh attempt |
| after arming, before active CAS | armed containment, no state ref | owner death is EOF before GO, so the Linux supervisor publishes a **no-command** receipt and exits without ever starting a command; on Windows nothing had started, so there is nothing to prove dead and no fact is required → orphan ignored; fresh attempt |
| after active CAS, before GO | active ref, unheld lease, **no-command** cleanup receipt | the §1 completion fact exists because arming precedes the CAS → ledger-only `interrupted`; explicit retry |
| after GO, before process exit | active ref, unheld lease, possibly live domain | require the §1 completion fact — a durable receipt on Linux → ledger-only `interrupted`, partial streams retained. **Windows and other POSIX have no readable fact and BLOCK for operator action**: on Windows the kernel really did terminate the domain, but no ordering between the lease handle and the job handle is guaranteed, so nothing a recovering process can observe proves it |
| after exit, before the guard is reacquired | active ref, streams, **no result** | ledger-only `interrupted` — the identity fact was never observed, so no outcome can be claimed |
| after final observation, before result published | active ref, no result | as above: `interrupted` |
| after result published, before outcome CAS | active ref + durable result | finalize the SAME attempt from the durable result |
| outcome visible, durability unconfirmed | outcome present | re-confirm; never double-apply |

**Non-crash launch and protocol failures (TURN-237 pin 3).** The table above covers owner death at
each cut; these are the failures where the coordinator is **alive** and something else went wrong. One
distinction governs them: **`spawn_failed` is a statement about the CONFIGURED TEST COMMAND**, used
only when that command could not start, and it points an operator at the run policy. A supervisor or
protocol fault is a **coordinator infrastructure fault** and is never recorded as `spawn_failed`. Both
map to `indeterminate` in §7, so the routing is identical — but the record is what a human reads, and
sending someone to debug their test command because a helper died belongs to the same family of lie as
routing an infrastructure failure to FIX.

| Failure | Attempt bound? | Result issued? | Recorded as |
|---|---|---|---|
| supervisor spawn failure, handshake failure, or arming deadline expiry — all **before** the CAS | **no** (bounded arming, §1) | no | typed coordinator error to the caller; no attempt, no ledger entry, no budget consumed |
| `GO` write fails after the CAS (`EPIPE` — the supervisor died) | yes | no | `interrupted`. Framing guarantees a truncated `GO` is not a `GO`, so no command started; the completion fact is still required before retry and **BLOCKS** if the supervisor died before publishing one |
| supervisor dies, or its frames are corrupt, **before** the command spawns | yes | no | `interrupted` — runner facts are untrustworthy, so no outcome may be claimed |
| supervisor dies, or its frames are corrupt, **after** the command spawned | yes | no | `interrupted`, partial streams retained; completion fact required, BLOCK when absent |
| the real command fails to start after `GO` | yes | **yes** | `TERMINAL{command_started: false, spawn_error}` → `execution: spawn_failed` → `indeterminate`, retryable, budget untouched — an authoritative outcome about the **policy**, not about the code |

In every row, an active attempt **cannot become retryable until the §1 cleanup completion fact is
proven**. A live-coordinator fault does not weaken that rule: the residue to be excluded is identical
to the crash case.

TOCTOU: identity is proven at start and again under the guard at finalization. Between them the guard
is released and an external writer can act — which is exactly why finalization re-proves rather than
trusting the start observation, and why `changed` is a first-class identity outcome.
